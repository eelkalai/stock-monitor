## Setup and run

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/python app.py
```

App runs at http://127.0.0.1:5000. There are no lint, test, or build commands configured — no test suite exists yet.

## Product overview

Local single-user Flask app for tracking a stock watchlist. Current capabilities:

- **Watchlist**: add a ticker by symbol (validated against Yahoo Finance before saving, rejects unknown symbols inline), remove a ticker (cascades its alerts), dashboard lists all tickers alphabetically with cached last price and % change.
- **Recent searches**: a separate "Search" box on the dashboard looks up any symbol and remembers it in a lightweight history list (most recent 10, re-searching a symbol just refreshes its entry instead of duplicating it) — unlike the watchlist, this is never background-polled (price is captured once, at search time) and never supports alerts. Selecting a recent search opens the same shared detail pane as a watchlist ticker, with an "Add to watchlist" button instead of alerts.
- **Buy from the stock view**: the shared stock detail pane (used on the dashboard and screeners pages, for both watchlist tickers and any other looked-up symbol) has its own inline "Buy" form that adds straight to the Portfolio without navigating away.
- **Price data**: background poller refreshes every ticker's price/change every 60s and caches it — the dashboard always reads from cache, never live, except when adding a ticker. Per-ticker historical chart with selectable range (1mo/3mo/6mo/1y/5y), fetched live per request. Any Yahoo Finance failure/rate-limit degrades to an empty result instead of erroring the page.
- **Alerts**: set an "above"/"below" price threshold per ticker, delete an alert. One-shot — once triggered the alert deactivates and won't re-fire.
- **Notifications**: bell icon with unread-count badge (polled via `/api/notifications/unread-count`), notifications page lists triggered alerts newest-first and marks them all read on view.
- **Live-update switch**: topbar toggle to pause/resume the background price poller (in-memory only, resets to on across restarts). Adding a ticker and viewing a chart still fetch live regardless of this switch.
- **Screeners**: drop-in Python scripts in `scripts/` implement custom stock-screening algorithms (not limited to the watchlist — a script can fetch/screen any symbols it wants, e.g. via `yfinance`'s `yf.screen()`). Each script gets a display name (its module docstring, e.g. `"""Top Gainers"""`, falling back to a prettified filename) and can declare parameters via a module-level `PARAMS = [{"name", "label", "type", "default"}, ...]` list — both are read via static `ast` parsing, without executing the script, so this stays fast regardless of how many scripts exist. The `/screeners` page has a picker (script dropdown + that script's param inputs + Run) for launching any discovered script; every Run opens a brand-new tab for that execution (labeled with the script's display name plus a param summary, e.g. "Top Gainers (count=5)") — running the same script again, even with the same params, opens another tab rather than reusing/overwriting one, so you can compare several runs (including different params of the same script) side by side. Tabs can be closed individually (×), and there is no in-place "re-run" — closing and re-launching from the picker is how you get a fresh run. The tab bar only ever shows tabs you've actually opened (not every discovered script), which keeps it manageable with a large number of screeners. Each run's results are cached in memory (module-level, resets on restart) keyed by a unique run id, not by script name; each run is isolated in its own subprocess with a timeout, so a hung or crashing script can't take down the app. Params are passed to the script as a JSON object in `argv[1]` (e.g. `{"count": 10}`).
- **Analysis**: drop-in Python scripts in `analyzers/` take the selected symbol as `argv[1]` and print a JSON object to stdout with a `recommendation` (plus optional `summary`/`metrics`/`chart`) — e.g. whether a stock is over/under-performing a target yearly gain. Same isolated-subprocess-with-timeout philosophy as screeners. The analysis pane is an always-visible third column alongside the shared stock detail pane (dashboard + screeners, not portfolio) whenever a stock is selected, with its own drag-resizable divider. The last analyzer run per symbol is cached in memory (resets on restart), so navigating away and back to a symbol redisplays its previous result without re-running.
- **Portfolio**: `/portfolio` tracks stocks you actually bought, independent of the watchlist. Buying a symbol (any symbol, validated the same way as adding a ticker) upserts a single aggregated `Holding` per symbol with a weighted-average cost basis; buying more of a symbol you already hold recomputes that average. Selling supports a partial quantity — a full sell closes (deletes) the holding, a partial sell just reduces it — and always writes a `RealizedTrade` record (quantity, cost basis, sell price, realized P&L) so the trade shows up under "Closed positions"; each closed-position row has its own "remove" action that deletes just that `RealizedTrade` record, dropping it out of the realized P&L total (this does not touch the `Holding` — it only forgets a historical closed trade). Price defaults to the current price (cached if the symbol is on the watchlist, live-fetched otherwise) if left blank on buy/sell. The background poller also records a portfolio-wide value/cost snapshot each cycle (skipped when there are no holdings) driving a value-over-time chart on the page.

Not present: no auth/multi-user support, no tests, no JSON API beyond the one unread-count endpoint, no editing of existing tickers/alerts (only add/delete). Any change to capabilities, design, or scope should be reflected in this section so it stays the source of truth for what the product currently does.

## Architecture

Single-process Flask app, five modules:

- `app.py` — `create_app()` builds the Flask app, wires SQLAlchemy to a local SQLite file (`stock_monitor.db`, gitignored), and creates tables on startup. All routes live directly in this file (no blueprints). `app = create_app()` is a module-level singleton. `start_scheduler(app)` is only invoked in the `if __name__ == "__main__"` block, so the background poller does not run under `flask run` or a WSGI server that imports `app.py` without executing it as `__main__`. `app.config["POLLING_ENABLED"]` (in-memory) gates the background poller and is injected into every template via a context processor. `_current_price(symbol)` and `_portfolio_context(...)` are shared helpers reused by the portfolio route and its buy/sell error-rendering paths. `_analysis_runs` (keyed by symbol) and `_screener_runs` (keyed by a unique per-execution run id from `_screener_run_seq`, also storing the script `name`/`params`/`tab_label` used) are module-level in-memory dicts, the same "resets on restart" precedent as `POLLING_ENABLED`, holding run results so they survive navigation without a database or session; `_screener_runs`' keys are also what determines which screener tabs are "open" — since each run gets its own id, running the same script twice produces two independent entries/tabs instead of overwriting one.
- `models.py` — seven SQLAlchemy models: `Ticker` (watchlist entry with cached `last_price`/`last_change_pct`), `Alert` (belongs to a `Ticker`, one-shot: `active` flips to `False` once `triggered_at` is set, it does not re-trigger), `Notification` (flat list, `read` boolean drives the unread-count badge), `Holding` (one aggregated portfolio position per symbol, weighted-average `avg_cost`), `RealizedTrade` (log of every sell, partial or full; individually deletable from the portfolio page to drop a closed trade out of realized P&L), `PortfolioSnapshot` (periodic total value/cost pair for the portfolio-over-time chart), `RecentSearch` (one row per recently-searched symbol, capped at `RECENT_SEARCH_LIMIT`, unrelated to `Ticker` — never polled, never has alerts).
- `stock_data.py` — the only module that talks to `yfinance`. Every function returns `None`/`(None, None)`/`[]` on failure instead of raising, so callers never need try/except around price data — this is what lets the app "degrade gracefully" on Yahoo Finance outages/rate-limits.
- `scheduler.py` — an APScheduler `BackgroundScheduler` polls every ticker's price every 60s (`POLL_INTERVAL_SECONDS`), updates cached price fields, and evaluates every active `Alert` for that ticker; a crossed alert deactivates itself and writes a `Notification` row in the same commit. It also computes a `PortfolioSnapshot` each cycle from current `Holding` rows (reusing prices already fetched for watchlisted symbols, live-fetching the rest), skipped entirely when there are no holdings. `poll_prices` no-ops immediately (but keeps firing on schedule) while `POLLING_ENABLED` is false — this single guard covers both ticker polling and portfolio snapshots.
- `screeners.py` — discovers screener scripts in `scripts/*.py`. `list_screeners()` returns `[{"name", "display_name", "params"}, ...]`: `display_name`/`params` are read via `ast.parse`/`ast.literal_eval` on the script's source (its module docstring and a top-level `PARAMS` list literal) without executing it — malformed/missing metadata falls back to a prettified filename and no params rather than erroring. `run_screener(name, params)` runs the script by name as an isolated subprocess (`sys.executable`, so it shares the venv) with a timeout, passing `params` (a dict, possibly `{}`) JSON-encoded as `argv[1]`, and parses its stdout as a JSON list of `{"symbol": ..., "price": ..., "change_pct": ..., "note": ...}` results. Mirrors `stock_data.py`'s never-raise convention — every failure (unknown name, timeout, non-zero exit, bad JSON) returns `(None, "error string")` instead of raising.
- `analyzers.py` — same shape as `screeners.py`, but discovers scripts in `analyzers/*.py` (`list_analyzers`) and runs one against a single symbol (`run_analyzer(name, symbol)`, symbol passed as `argv[1]`), validating stdout is a JSON *object* with a non-empty `"recommendation"` string (instead of a list of `{"symbol": ...}` dicts). Same never-raise, isolated-subprocess-with-timeout convention.

Templates (`templates/`) are server-rendered Jinja with routes doing full-page or redirect-based updates (no SPA/JS framework, aside from a small `static/split-view.js` that AJAX-swaps the shared detail-pane and analysis-pane fragments on the dashboard/screeners pages) — `base.html` is the shared layout with the alerts bell, live-update switch, and screeners/portfolio nav links; `dashboard.html`/`ticker.html`/`notifications.html`/`screeners.html`/`portfolio.html` extend it. Dashboard and screeners render a 3-pane list/detail/analysis split-view (`.list-pane`/`.detail-pane`/`.analysis-pane`, joined by `.split-divider` elements); `split-view.js`'s resizer generalizes over however many `.split-divider`s are present, so this isn't hardcoded to two panes. The portfolio page deliberately does NOT use the AJAX fragment (`_stock_detail.html`/`_stock_analysis.html`) — its holdings list uses plain full-page navigation for selection, to avoid adding portfolio-specific branching to infrastructure the dashboard/screeners pages also depend on.

### Request flow for prices

Ticker prices shown on the dashboard are the *cached* `last_price`/`last_change_pct` columns, refreshed only by the background scheduler — routes never fetch a live quote for display except when adding a new ticker (`symbol_exists` + `fetch_quote` in `add_ticker`) or loading history (`ticker_detail` calls `fetch_history` live, per request, uncached).

## Development workflow (subagents)

Code changes go through a design-then-execute pipeline, defined in `.claude/agents/`: a top-tier model designs and writes the instructions, a smaller model writes the code.

1. **`architect`** (Opus) — for any feature or non-trivial fix, invoke this first with the user's request. It reads the code, makes every design decision, and writes a step-by-step spec to `.claude/specs/<slug>.md` (gitignored). It never edits production code.
2. **`implementer`** (Sonnet) — invoke with the spec path. It executes the spec literally and runs its verification checks. It does not design: if the spec is ambiguous or doesn't match the code, it stops and reports rather than improvising.
3. If the implementer reports a blocker or deviation, send that report back to `architect` to revise the spec, then re-run `implementer` — don't patch around it in the main session.

Pass the spec by path, not by pasting its contents. Trivial edits (a typo, a one-line constant, a copy change) can skip the pipeline and be made directly. `debugger` (Sonnet, diagnose only), `code-reviewer` (Opus, read-only review), and `tester` (Sonnet, only when tests are explicitly requested) sit alongside this pipeline — a `debugger` diagnosis feeds `architect`, not `implementer` directly.
